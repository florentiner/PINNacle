# Абляция DQN-стека агента: расширение на весь бенчмарк

Абляция отвечает на вопрос рецензента DV8H (Q4): какие компоненты DQN-стека
несут нагрузку. Режимы — полный агент и три «минус компонент»:

| режим | что выключено |
| --- | --- |
| `none` | ничего (полный агент: PER + soft-Watkins + trust-region) |
| `no_per` | prioritized replay: равномерная выборка без приоритетов и IS-весов |
| `no_soft_watkins` | soft-Watkins Q(λ): вместо него 1-step Double DQN таргет |
| `no_trust_region` | trust-region маска в лоссе |

Метрика — доля успешных траекторий (success rate) и итоговая L2RE, обе по
нескольким независимо обученным агентам.

## Что уже посчитано

Кампания `runs_kaggle_v5` (HF-датасет `danil-e/rlpinn-ablation-runs`), три
уравнения — `poisson_boltzmann_2d`, `poisson3d_complexgeometry`,
`ns2d_liddriven`. Эти числа вошли в rebuttal. Пересчитать их таблицу из сырых
CSV:

```bash
python experiments/agent_ablation/collect_results.py --prefix runs_kaggle_v5 \
    --out ablation_v5_recomputed.csv
```

(Сходится с опубликованной `runs_kaggle_v5/ablation_v5_final.csv` во всех
ячейках, кроме `poisson3d_complexgeometry/no_trust_region`, где
`l2re_min_median` отличается на 3%: в опубликованной таблице там медиана по
успешным, в остальных ячейках — по всем траекториям. Пересчёт из сырых CSV
считается верным, поэтому в новой таблице обе колонки лежат рядом.)

## Протокол — как в ответе ревьюерам

Из комментария авторов от 03.08.2026 (вопрос 4 рецензента DV8H), дословно:
«on three PDEs, removing one component at a time from the full agent. Single
seed per configuration, same PINN budget throughout. Success rate is the
fraction of constructed chains that reach the stopping criterion; trajectory
counts differ per cell, so the rate rather than the raw count is the
comparable quantity.»

Отсюда три вещи, которые расширение не меняет:

* **один сид на конфигурацию** — не 5 и не 10; несколько сидов были бы
  улучшением протокола, а не его исполнением, и упираются в недельную
  GPU-квоту Kaggle;
* **одинаковый бюджет PINN** во всех режимах;
* **отчётные метрики — success rate и медианная L2RE**, причём медиана
  считается по успешным цепочкам: в опубликованной таблице ячейка
  `poisson_boltzmann_2d / no PER` пуста именно потому, что успешных цепочек
  там не было ни одной. `collect_results.py` кладёт эту таблицу рядом с CSV
  (`<out>.rebuttal.md`).

Текущая кампания — `runs_kaggle_v7`: шесть новых уравнений (`grayscott`,
`heatnd`, `heatinv`, `poissoninv`, `ns2d_backstep`, `burgers2d`) в четырёх
режимах, сид 1234, плюс контрольный `poisson_boltzmann_2d` — уравнение из
опубликованной таблицы, пересчитанное тем же критерием, чтобы расширенные
числа стояли на одной ноге с уже отправленными.

### 2. Порог успеха

Критерий успеха траектории взят из статьи, а не придуман: формула (11)
останавливает эпизод при `e(theta) <= eps`, где `e(.)` — **ошибка против
эталонного решения**, и раздел 3 повторяет это словами («we monitor the RMSE
between the predicted PINN solution and the reference solution»). Ответ
ревьюерам подтверждает: в таблице «Ground-truth usage» строка «Stopping
criterion (agent training): Yes».

Раннер считает успех по `--success-metric`:

* `l2re` (по умолчанию) — относительная L2-ошибка против эталона, та самая
  величина, что в таблице 1 статьи: нормированная и сравнимая между задачами;
* `rmse` — `E = lambda_op*RMSE_op + lambda_bc*RMSE_bc` буквально по формуле (15);
* `loss` — взвешенный train loss; так считалась кампания v5 и loss-вариант из
  ответа ревьюерам. Оставлен для воспроизведения старых чисел.

Длина цепочки ограничена `Kmax = 10` (формула 11), а не 12, как было в коде.

**Значение eps не задано ни в статье, ни в ответе ревьюерам** — это
единственная свободная величина. Поэтому она привязана к уже опубликованному
числу: `eps = EPS_FACTOR x L2RE` из таблицы 1 (колонка PELINE), `EPS_FACTOR = 2`.
Множитель выбран по 116 траекториям первой попытки (там ранней остановки не
было, цепочки шли все 12 шагов, поэтому `l2re_min` показывает, чего цепочка
достигает за полный прогон). Доля траекторий, укладывающихся в `k x эталон`:

| уравнение | k=1.0 | k=1.25 | k=1.5 | **k=2.0** |
| --- | --- | --- | --- | --- |
| `grayscott` | 0% | 23% | 23% | 46% |
| `heatinv` | 0% | 77% | 85% | 100% |
| `heatnd` | 0% | 6% | 25% | 75% |
| `ns2d_backstep` | 3% | 83% | 93% | 97% |
| `poissoninv` | 0% | 0% | 0% | 87% |

Единого «правильного» множителя нет. При `k = 1.0` (ровно опубликованный
эталон, без всякой свободной константы) цель недостижима ни на одном
уравнении: тренировочные эпизоды короче и агент в них ещё учится, тогда как
эталон в таблице 1 — результат ОБУЧЕННОГО агента на бюджете 7000 эпох. При
`k <= 1.5` обнуляется `poissoninv`: его достижимая L2RE лежит на 1.87–1.94x
эталона. `k = 2.0` — единственное значение, при котором измеримы все пять.

Чего ожидать: цепочки выходят короткие (медиана 1–2 шага), но в кампании v5
было так же (PB2D — 2 шага, Poisson3d-CG — 3–4), то есть для этого метода это
норма. Часть уравнений может дать ~100% во всех режимах — такая строка не
испорчена, а читается как «здесь компонент не нужен»: ровно так в v5 вышел
Poisson3d-CG, и ответ ревьюерам это докладывает («where nearly every trajectory
succeeds, there is little to prioritise»).

Почему это пришлось менять: с критерием по train loss пять уравнений из пяти
давали либо 0%, либо 100% успеха во всех режимах. Взвешенный train loss живёт
в своей шкале, не связанной ни с эталоном, ни с буфером, и у каждого уравнения
она своя (у `heatnd` ~1e-4, у `heatinv` ~200), поэтому любой порог получался
либо тривиальным, либо недостижимым.

#### Порогов два, и это не одно и то же

Онлайн-критерий (`tolerance` -> `EnvRLOptimizer`) сравнивает **ошибку против
эталонного решения**. Разметка офлайн-буфера (`buffer_tolerance` -> загрузчик
переходов) сравнивать её не может: в сохранённых переходах эталона нет, там
лежат только `loss_total` / `loss_oper` / `loss_bnd`. Поэтому буфер
размечается откалиброванным по нему **лосс-порогом** — тем самым `tolerance`
из реестра, который считают `calibrate_tolerance.py` и `prepare_pde.py`.

Пока обе величины передавались одним параметром, `done=1` в буфере ставился
сравнением лосса с L2RE-порогом, то есть величин разной природы. На реальных
буферах это давало вот что:

| уравнение | одним порогом (неверно) | двумя порогами |
| --- | --- | --- |
| `poissoninv` | 0 успешных / 1138 провальных | 870 / 288 |
| `heatinv` | 1 / 1210 | 1021 / 278 |
| `grayscott` | 81 / 477 | 618 / 160 |
| `burgers2d` | 48 / 248 | 378 / 66 |
| `ns2d_backstep` | 791 / **0 провальных** | 575 / 191 |
| `heatnd` | 275 / 50 | 294 / 38 |

То есть предобучение на 500 шагах шло по вырожденной разметке: на `poissoninv`
и `heatinv` квота успешных цепочек в батче («forced inclusion of successful
chains in every batch» из ответа ревьюерам) оказывалась пустой, а на
`ns2d_backstep` в буфере не было ни одного провала. Отсюда правило: **новое
уравнение нельзя запускать без калиброванного лосс-порога**, даже когда
кампания идёт по `--success-metric l2re`.

### 4. Кампания на Kaggle

Токены аккаунтов — в `~/.kaggle/ablation_accounts.tsv` (строки
`<аккаунт><TAB><токен>`), HF-токен — в `~/.rlpinn_campaign/hf_token`. Оба

Про формат токенов: новые токены Kaggle (`KGAT_...`) работают **только**
через `KAGGLE_API_TOKEN` (CLI ходит с Bearer); в `KAGGLE_KEY` такой токен
даёт 401. Старые 32-символьные ключи — через `KAGGLE_USERNAME`/`KAGGLE_KEY`,
в файле аккаунтов они пишутся как `classic:<user>:<key>`.

```bash
# 1. живы ли аккаунты (только чтение)
python experiments/agent_ablation/kaggle/build_campaign.py accounts

# 2. разложить ячейки по аккаунтам волнами (5 сидов по умолчанию)
python experiments/agent_ablation/kaggle/build_campaign.py plan \
    --tier solvable --tier borderline --skip-done --prefix runs_kaggle_v6

# 3. собрать пуш-пакеты волны (вне репозитория)
python experiments/agent_ablation/kaggle/build_campaign.py build --wave 1

# 4. запушить (запускает счётчик GPU-квоты)
python experiments/agent_ablation/kaggle/build_campaign.py push --wave 1 --yes

# 5. следить
python experiments/agent_ablation/kaggle/build_campaign.py status --wave 1
```

Одна ячейка = цепочка сессий: сессия идёт 10.5 ч (лимит Kaggle 12), сама
останавливается, сохраняет агента и метрики на HF, следующая сессия той же
ячейки подхватывает чекпоинт (`RESUME=auto`). Чтобы добрать траекторий,
достаточно запушить ту же волну ещё раз.

Кернел клонирует ветку `rlpinn_agent_ablation` из `florentiner/PINNacle` и
падает с внятным сообщением, если в клоне нет `ablation_chain.py`: **сначала
код в ветку, потом пуш кернелов**. Для воспроизводимости волну можно
прибить к коммиту: `plan --commit <sha>`.

Одной сессии на ячейку хватает на 10–40 траекторий у дешёвых уравнений и на
~10 у дорогих (по таймингам v5: `poisson_boltzmann_2d` ~2.5 ч на 10
траекторий, `ns2d_liddriven` ~4–9 ч, `poisson3d_complexgeometry` ~8.5–12 ч).

Цена претрена измерена: 500 шагов x 5 батч-апдейтов = 1330 с (~22 мин) на
CPU этого ноутбука, при двух процессах разом; на Kaggle-GPU меньше. То есть
~3% от 10.75-часовой сессии, и платится один раз на ячейку: при
`RESUME=auto` продолжающие сессии претрен пропускают.

## Что нашёл аудит перед запуском кампании

Пять правок в общем коде (`rl_trainer.py`, `RL/`), каждая — реальная ошибка,
которая испортила бы именно расширенную кампанию:

1. **`--seed` ничего не сидировал.** В `train_process_rl` вызов
   `dde.config.set_random_seed(seed)` был закомментирован, поэтому «разные
   сиды» отличались только недетерминизмом процесса. Для кампании, где пять
   независимо обученных агентов на ячейку — это половина смысла, теперь сид
   выставляется (проверено: одинаковый сид даёт побитово те же лоссы, разные —
   разные). При продолжении сессии к сиду добавляется сдвиг от тега прошлого
   запуска, иначе каждая следующая сессия повторяла бы ту же
   последовательность инициализаций PINN.
2. **Резюм подхватывал чужой чекпоинт.** `resolve_resume_checkpoint` искал
   последний запуск пары (уравнение, режим) без учёта сида. Проверено на
   данных v5: запуск `seed4321` на `poisson3d_complexgeometry/none`
   продолжился с агента `seed1234` — то есть «двух независимых агентов» в той
   ячейке не было. Теперь фильтр по `_seed<N>` в теге запуска обязателен.
3. **Дедлайн проверялся только между траекториями.** Траектория идёт 1–3 часа,
   поэтому начатая незадолго до `--max-hours` упиралась в 12-часовой лимит
   Kaggle и сессия умирала без финального чекпоинта агента — цепочка сессий
   ячейки теряла всё обучение сверх последнего периодического снапшота.
   Теперь после дедлайна не начинается новый чанк оптимизатора. Бюджет сессии
   снижен до 10.5 ч: чанк L-BFGS на тяжёлом уравнении досчитывается до часа.
4. **Финальная выгрузка на HF не переживала 429.** Полсотни сессий кампании
   коммитят в один датасет; `upload_folder` падал с первой попытки, а в этой
   выгрузке — единственная копия `agent_final.pt`. Теперь до 5 попыток с
   растущей паузой и джиттером, период штатной синхронизации поднят с 900 до
   1800 с (вдвое меньше коммитов в час).
5. **Расписание ε и warmup PER не соответствовали претрену 500.**
   `steps_done` растёт и на оффлайн-претрене, поэтому при `EPS_DECAY=50` агент
   выходил в онлайн с ε уже на минимуме (0.05) — исследование выключено с
   первого шага. В ветке Saitama32 вместе с претреном 500 стоит `EPS_DECAY=200`
   и `warmup_updates=200`; раннер теперь передаёт их явно (`--eps-decay`,
   `--warmup-updates`), старые раннеры сохраняют прежние дефолты.

Плюс две правки в агрегаторе и загрузчике:

* success rate считается от завершённых траекторий (`done=1` + `done=-1`);
  прерванная дедлайном траектория (`done=0`) в знаменатель не идёт, иначе
  режим выглядел бы тем хуже, чем неудачнее лёг конец сессии. На данных v5
  результат не меняется — там прерванных траекторий нет;
* точечный фильтр битых наград в загрузчике буфера (список из трёх значений,
  заведённый когда-то под Burgers) применяется ко всем уравнениям и молча
  выбрасывал переходы. На трёх существующих буферах он не срабатывает ни разу,
  но `burgers1d`/`burgers2d` в кампании есть — теперь он считает выброшенное и
  пишет итог в лог.

Что осталось известным ограничением, а не багом: буфер грузится в
`PrioritizedReplayBuffer(10000)`, и уравнение с большим числом переходов
(у `ns2d_liddriven` их 11631) затирает самые ранние. Так считалась и кампания
v5; менять размер — значит менять условия сравнения.

## Что проверено на существующих буферах

Кампания ещё не запускалась; код прогнан на трёх буферах, которые уже лежат
на HF:

* `smoke_test_registry.py` — 21 из 21 уравнения реестра собирается
  (`convection_beta50` помечен нереализованным и пропускается);
* `smoke_test_registry.py --train-iters 100` — на всех 16 уравнениях кампании
  проходит настоящий чанк Adam с теми же колбэками, что в RL-цикле: взвешенный
  train loss конечен, метрики оператора и границы считаются (нигде не NaN),
  снимки весов для ландшафта сохраняются;
* `smoke_test_ablation.py` — все четыре режима абляции обучаются на
  синтетическом буфере, приоритеты PER ведут себя как задумано;
* `smoke_test_hf_buffer.py --pde ns2d_liddriven` — реальный буфер с HF
  грузится и обучает агента во всех четырёх режимах (11631 транзишен,
  178 успешных терминалов);
* `ablation_chain.py --pde ns2d_liddriven --n-trajectories 0
  --offline-pretrain-steps 500` для режимов `none` и `no_per` — полный путь
  раннера на CPU: скачивание буфера, все 500 шагов претрена без NaN,
  диагностика жадной политики (она воспроизводит цепочку PSO -> Adam ->
  L-BFGS из успешных эпизодов буфера), сохранение агента, `status.json`, CSV;
* параметры раннера (`AE_model_params`, `AE_train_params`,
  `loss_surface_params`, `rl_agent_params`) совпадают с
  `poisson_boltzmann_2d_ablation_chain.py` из v5 построчно, кроме
  параметризации по уравнению и претрена 50 -> 500;
* `collect_results.py --prefix runs_kaggle_v5` воспроизводит опубликованную
  таблицу v5 (одно расхождение описано выше) — в том числе после смены
  знаменателя success rate;
* сид: два запуска с одним сидом дают побитово одинаковые лоссы агента,
  с разными — разные; резюм с фильтром по сиду проверен на реальных тегах v5;
* `build_campaign.py accounts` — 27 из 27 Kaggle-аккаунтов авторизуются;
  `plan`/`build` собирают пакеты с уникальными kernel id, токен попадает
  только в копии вне репозитория.

## Совместимость с кампанией v5

Кампания v5 считалась с оффлайн-претреном 50 шагов, новая — с 500, поэтому
числа между префиксами напрямую не сравниваются. Уравнения v5 в расширенной
кампании нужно пересчитать заново (они в реестре помечены `campaign=done`,
`plan --skip-done` их исключает — снимайте флаг, когда пересчитываете).

Старые per-PDE раннеры `experiments/optimization_multi_pde/*_ablation_chain.py`
оставлены как есть: по ним воспроизводится v5.
